# ツギココ

気になったら、ツギココ。

飲食店・カフェの「行きたい」を記録するWebサービスです。仕様・技術スタック・設計方針は[CONTEXT.md](CONTEXT.md)を参照してください。

## 開発環境

Node.js 22系とnpmを使用します。App Hostingのビルド環境も22系に指定しています。

```sh
npm install
npm run dev
```

http://127.0.0.1:3000 を開きます。

この開発環境のTurbopackの起動制限を避けるため、開発・本番ビルドにはNext.jsのWebpackオプションを使用しています。

## 現在の実装

- スマートフォン中心のログイン前トップページ
- Firebase AuthenticationによるGoogle・X・Facebookの登録・ログイン・ログアウト
- URLからの店舗登録、非公開マイリスト、用途別リスト（複数所属・未分類・名前変更・削除）、店名・住所・メモの編集、30日間のごみ箱
- 公式サイトなどの構造化データ（JSON-LD）からの店名・住所・料理ジャンルの自動入力。取得できない場合は手入力
- 非公開の訪問記録（訪問日・任意の星1〜5・任意の感想）、再訪履歴、記録の編集・削除
- ログイン状態の維持と未ログイン時の`/home`から`/login`への移動
- スマートフォン中心のログイン後ホーム（マイリスト・ユーザー横断のおすすめ）
- アカウント表示、認証方法の追加・解除（最後の方法は解除不可）
- URL入力の検証と、ログイン完了後のマイリストへの自動保存
- 保存操作を試せる画面内デモ
- モバイルメニュー、FAQ、プライバシー説明、画像クレジット

Google・X・Facebook認証と店舗保存は実際のFirebaseに接続します。訪問記録・評価と、ユーザー横断のレコメンドを利用できます。ログイン前にURLを入力して「保存してはじめる」を押すと、ログイン完了後にFirestoreへ非公開で自動保存します。URLは保存成功まで`sessionStorage`でログインしたユーザーにひも付けて保持し、失敗時は入力欄から再試行できます。再読み込みや同じURLの再試行でも、サーバーで重複を防ぎます。未保存のURLはログアウト時に消去しますが、登録済みの店舗はログアウト後も残ります。公開トップページは検索エンジン向けにindex, followを指定し、それ以外の画面はnoindex, nofollowを維持しています。

### トップページの登録導線と見本

ヒーローの「URLなしではじめる」は入力欄のURLを引き継がず、登録ダイアログを開きます。モバイルでは説明・登録導線を写真より先に表示します。Instagram・Xは投稿内容を取得せずURLを保存し、同じURLの登録済み店名・住所・ジャンルがあれば初期値に使います。公式サイトなども取得できる場合だけ補完します。マイリスト・おすすめの見本は架空の入力済みデータで、写真はイメージです。デモのボタンは表示の切替だけを行い、サーバーへの店舗保存やおすすめの取得を行いません。おすすめが登録直後に必ず表示されるという説明はしません。

## 認証設定

- `src/lib/firebase/client.ts`はWebアプリの公開設定です。サービスアカウント鍵やOAuthシークレットは含みません。
- Google認証の設定は`firebase.json`で管理し、`firebase deploy --only auth --project tsugikoko`で反映します。
- Firebase Authenticationの承認済みドメインに、公開ドメイン・`localhost`・`127.0.0.1`を設定済みです。同一メールアドレスで複数アカウントを作成する設定は無効です。
- 認証はFirebase SDKのポップアップを利用します。閉じた場合・ブロック・通信失敗は画面内で案内します。SNS内ブラウザではSafari/Chromeで開き直してください。
- 初回認証はアカウント登録を兼ねます。既存ユーザーには以前と同じ方法を選ぶよう案内し、新しい方法はログイン後に`linkWithPopup`で同一UIDへ連携します。メールアドレスや表示名だけで独自に統合しません。
- X・Facebookのログイン・既存アカウントへの連携を有効にする構成です。Appleも処理は実装済みですが、外部設定が未完了なので「準備中」と表示します。

## 独自ドメインとSNS共有

公開URLは`https://tsugikoko.com`です。`src/lib/site.ts`で管理し、トップページのcanonical・OGPに使用します。認証用の`authDomain`とコールバックは`tsugikoko.firebaseapp.com`を維持し、Cloud Tasksの内部配送先は`hosted.app`のままにします。Firebaseの承認済みドメインには`tsugikoko.com`と`www.tsugikoko.com`を登録済みです。旧ドメインから移動した際は、ブラウザのログイン状態がドメインごとに保存されるため再ログインしてください。

マイリスト・おすすめカードの「共有」から投稿内容を確認し、X・LINEの投稿画面へ進めます。対応端末では標準の共有メニューも利用でき、投稿文のコピーにも対応します。共有するのは店名と元ページのURLだけで、メモ・訪問記録・評価・UIDは含めません。記録の公開設定は変更しません。SNSへの最終送信は本人が各SNSで行い、投稿APIや投稿用アクセストークンは利用しません。XでのログインとXへの共有は別の機能で、共有にはツギココへのX連携は必要ありません。

## 店舗登録と自動入力

### 用途別の非公開リスト

- マイリスト上部の「リスト管理」で作成・名前変更・削除します。名前は40文字以内、1人50件まで。同じ名前（全角半角・英字の大小を正規化）は重複作成せず、既存のリストを使います。
- 店舗カードの「リストを選ぶ」で複数所属を選択し、「所属を保存」で確定します。選択中にも新しいリストを作成できます。URL登録はリスト選択を必須にせず、保存後に追加操作を案内します。
- 「すべてのお店」「未分類」または任意のリストを選び、検索・ジャンル・訪問状況・並び順を組み合わせます。登録順は店舗の保存日時で、リストへ追加した日時ではありません。条件変更では先頭ページから取得します。
- リストから外しても、リスト自体を削除しても、店舗・メモ・訪問履歴は残ります。リストの削除には確認を挟み、リスト自体の復元はありません。店舗をごみ箱に移した場合は所属を保持し、復元時に存続するリストへ戻します。店舗の統合では両方の所属を重複なく引き継ぎます。
- `users/{uid}/settings/placeLists` の `items` に最大50件の定義（ID・名前・作成/更新時刻）、`savedPlaces` の `listIds` に所属を保存します。既存データの所属欠損は未分類として扱い、一括移行は不要です。定義と所属の更新はトランザクションを使い、別画面での競合を検出します。
- リスト削除時は定義だけを削除し、有効な定義のIDとの積集合で所属を解決します。保存記録に残る削除済みIDは表示・検索上は所属として扱わず、所属更新・店舗統合時に除去します。サーバー生成IDは再利用しません。大量の店舗を一括更新するジョブは不要です。
- `/api/places/lists` の GET/POST と `/api/places/[id]` の PATCH（`setLists`）を使います。認証済み本人のユーザー配下だけを操作し、変更には既存の書き込み制限が適用されます。名前や所属を共通店舗・推薦モデル・アクセス解析へ送らず、退会時にユーザー配下の再帰削除で削除します。
- 指定リストの通常一覧はインデックスで対象を絞って30件ずつ取得します。検索・ジャンル・店名順では対象リストの店舗を全件読みます。「未分類」は削除済みIDや旧データも扱うため、本人の該当状態の店舗を全件読みます。全件読み取りになる検索・未分類では定期ポーリング・画面復帰の自動再取得を止めます。インデックスで取得する通常のリスト指定では自動更新を継続します。
- 本番反映時は、アプリより先に `firebase deploy --only firestore:indexes --project tsugikoko` で追加した複合インデックスを反映し、構築完了を確認してください。エミュレーターの成功だけでは本番のインデックス構築を確認できません。公開・共有・共同編集・手動順序・一括操作は未実装です。

### 登録・取得の詳細

#### Googleマップの表示時取得

- Googleマップの保存カードが画面に入ったとき、本人認証付きの `POST /api/places/[id]/google-details` でPlaces API (New)へ問い合わせます。画面外・ごみ箱・店名と住所が両方入力済みのカードは問い合わせません。同じカードの通常の一覧更新では再取得せず、画面を開き直すと再取得します。
- 特定不能（422）になった記録には制御用の `googleLookupFailedAt` を付け、以後はサーバー・画面の両方で自動再取得を止めます。手入力と元リンクは利用できます。一時的な通信障害・上限到達はこの停止対象にせず、開き直した際に再試行できます。同じ記録を30秒以内に開き直した場合は、上限到達と区別して待機を案内します。
- 対応URL形式を将来拡張するときは、対象の既存記録の `googleLookupFailedAt` を解除する移行も検討してください。現時点では利用者が解除する操作はありません。短縮先の429・5xxなどは恒久停止にせず、一時エラーとして扱います。
- `maps.app.goo.gl` / `goo.gl/maps` は転送先ヘッダーだけを確認し、Googleマップの許可ホスト以外には接続しません。Place ID入りURLはPlace Details、店名入りURLはText Searchを使います。CIDがあれば応答のMaps URLと一致を確認し、CIDがない場合は同名の複数候補を自動選択しません。CIDだけ・座標だけ・経路・本文を読む必要があるリンク・特定できないリンクは手入力へ戻ります。GoogleマップのHTML本文を解析する処理はありません。
- Google由来の店名・住所はカード内のGoogle Maps帰属表示付き領域で表示し、Reactの表示中の状態だけに置きます。ブラウザー保存・Firestore・共有文・編集初期値・`places` / `placeSources` / `urlFacts`・おすすめへ混ぜません。永続化するGoogle由来の値は本人の記録内の `googlePlaceId` だけです。取得制御用の時刻・nonceも本人の記録内に持ち、退会時は再帰削除の対象です。検索・ジャンル・並び替え・おすすめは従来の保存済み情報を使用します。
- サイト全体でUTC日次100回、UTC月次4000回、本人ごとに1分6回・1日30回、同じカードは30秒に1回まで。Firestoreトランザクションで送信前に枠を予約し、失敗も消費します。1回の取得でPlaces APIを呼ぶのは最大1回です。`GOOGLE_PLACES_DAILY_LIMIT` / `GOOGLE_PLACES_MONTHLY_LIMIT` で上限を下げられます（0で停止、最大100/4000）。制御情報は `serviceLimits/googlePlaces` と `users/{uid}/limits/googlePlaces` に保存します。
- 取得中の削除や別リクエストによる競合で表示結果を破棄した場合も、予約した回数は戻しません。特定不能なURLの初回確認も1回消費しますが、それ以降は自動停止により消費しません。
- APIの必要項目だけを取得します。2026年10月28日の公式料金では、Place Details Pro / Text Search Proはそれぞれ月5000回の無料枠、超過後の最初の料金帯は1000回17 / 32米ドルです。本実装の上限はこのアプリの呼び出しだけを対象とし、同じ請求先の他プロジェクトの利用やGoogleの料金改定を含めた請求上限を保証しません。[料金](https://developers.google.com/maps/billing-and-pricing/pricing) / [保存・帰属表示の条件](https://developers.google.com/maps/documentation/places/web-service/policies)
- 有効化にはGoogle Cloudの `places.googleapis.com` と、そのAPIだけを許可したサーバー用キーが必要です。`GOOGLE_PLACES_API_KEY` はSecret Manager経由でApp HostingのRUNTIMEだけに渡し、`NEXT_PUBLIC_` 変数・リポジトリ・ログへ入れません。キー未設定では取得せず、URL保存と手入力を案内します。既存のFirebase用ブラウザーキーを流用しません。
- tsugikokoプロジェクトでは2026年10月29日にAPIと専用キーを設定済みです。`apphosting.yaml` は `tsugikoko-google-places-api-key@1` をRUNTIME限定で参照します。App HostingバックエンドへのSecretアクセスを公式CLIで付与し、実APIのPlace Details応答を1回確認しました（取得内容・キーはログやファイルへ保存せず、本番の店舗データも変更していません）。アプリの本番反映は別途必要です。

- `/api/places`で登録と30件単位の一覧取得、`/api/places/[id]`で編集・再取得・ごみ箱・復元を行います。
- カードには「再取得」ボタンを表示しません。店名が未入力の場合だけ「編集」を緑色のボタンで強調し、手入力を案内します。店名の保存後は通常の編集ボタンに戻ります。再取得API（`PATCH`の`retry`）は自動入力の対象URLに限って残しています。
- マイリスト・ごみ箱は先頭30件を表示し、末尾の300px手前までスクロールすると次の30件を自動で読み込みます。追加取得は重複実行を防ぎ、失敗時は表示済みの店舗を残して末尾から再試行できます。「もっと見る」は手動操作・自動読み込み非対応環境用にも残します。通常一覧の定期更新・画面への復帰・編集後も読み込み済みのページ数を維持し、タブや検索条件を切り替える前の古い応答は反映しません。
- マイリストは店名・住所・自分用メモの部分一致検索、ジャンル（未設定を含む）の絞り込み、登録が新しい順／店名順の並べ替えに対応します。行きたい／訪問済み／ごみ箱と組み合わせ、未読込の記録も対象にします。検索は入力確定後に検索ボタンで実行し、空白区切りの語はAND、全角半角と英字の大小を正規化します。条件変更では先頭30件に戻り、その後は遅延取得します。新規URLの保存後は条件を解除して一覧へ戻します。
- `GET /api/places` の追加パラメーターは `q`（100文字以内）、`genre`（`all`／`unset`／ジャンルID）、`sort`（`newest`／`name`）です。店名順は日本語の照合順で、ふりがな順ではありません。未入力の店名は末尾、同名は登録日時とIDで順序を固定します。
- 試作の検索・ジャンル絞り込み・店名順は、リクエストごとに本人の通常記録またはごみ箱を全件読み、サーバーで絞り込みます。300件保存していれば1ページの取得でも300件分を読みます。追加の検索サービスは使いません。読み取りを抑えるため、条件が有効な間は定期ポーリングと画面復帰時の自動更新を止め、検索ボタンの再実行・編集後などで更新します。通常一覧は従来どおり30件単位です。利用増加時には検索用インデックスやキャッシュを検討します。
- 店舗カードの上部には、判定できた料理ジャンルに対応する共通のイメージ写真を表示します。ジャンルが不明な場合は、店舗IDごとに固定した4色の淡い背景と装飾アイコンを表示します。不明ジャンルの装飾はCSS・SVGで描画します。一覧の見出し・検索欄・絞り込み・タブ・追加操作は固定せず、ページと一緒にスクロールします。装飾の色・アイコンは店舗のジャンルや評価を表しません。
- `users/{uid}/savedPlaces`に本人の記録、`places`に確認済みの共通店舗情報、`placeSources`に取得元と1日分の再利用情報を分けます。本人が入力した店名・住所・ジャンルは、`urlFacts`に必要項目だけを保存し、同じ正規化URLを別ユーザーが登録したときの入力補助に再利用します。メモ・訪問・星評価・UID・追加のURLは再利用しません。
- 同じURLは追跡パラメータを除いて正規化し、トランザクションで重複登録を防ぎます。食べログの口コミ・写真ページ、一休のプランページ、XやInstagramの共有URLも店舗・投稿単位に揃えます。異なる取得元の共通店舗照合は、自動入力できた店名と住所の完全一致を使い、名前だけで支店を統合しません。
- 保存・編集・再取得の合計は、試作時は1ユーザーあたり20回/分・200回/日。再取得は1分間隔、通常の取得結果は1日再利用します。本人による「再取得」では10分より古い結果を使わず元ページを読み直します。取得方式のバージョンが変わった場合は古いキャッシュを使いません。
- URLを先に保存し、本番ではCloud Tasksのジョブで取得を継続します。外部取得は8秒・1.5MBまでとし、リダイレクトを追いません。中断した処理はFirestoreの状態を基に一覧再表示時に最大3回まで再開します。Cloud Tasks無効時は90秒の処理リースが切れれば再開でき、ジョブ登録日時には左右されません。登録から10分間のジョブ再登録待ちはCloud Tasks有効時だけ適用します。
- Cloud Tasksのキュー`place-extraction`（asia-east1）・呼び出し用サービスアカウント・必要な権限を構築し、`PLACE_TASKS_ENABLED=true`に設定しました。内部APIはOIDCで呼び出し元を検証します。ローカル・エミュレーター、または`PLACE_TASKS_ENABLED=false`の環境ではCloud Tasks APIを呼ばず`after`を使い、内部APIは401を返します。無効時はプロセス異常終了からの復旧に一覧の再表示が必要です。
- 自動補完は本人の追記を上書きしません。写真・紹介文・口コミ・OGP画像は保存・表示せず、独自のアイコンを表示します。
- ごみ箱は30日間復元可能です。`purgeAt`のTTLで保存記録を削除し、期限超過した記録はTTLの実行待ちでもAPIから非表示にします。共通店舗情報とURL対応用のハッシュは別管理です。

### 訪問記録と評価

- カードの「行ってきた」から訪問日、星1〜5（任意）、感想（任意・2,000文字以内）を記録します。日付の初期値は日本時間の今日で、未来日・実在しない日付はサーバーでも拒否します。未評価は`null`として星の値と区別します。
- 1件でも訪問記録がある店舗は「訪問済み」、0件なら「行きたい」に表示します。再訪は別の記録として残し、編集・確認付きの削除ができます。最後の記録を削除すると「行きたい」に戻ります。
- `PATCH /api/places/[id]`の`addVisit`・`editVisit`・`deleteVisit`で更新し、`GET /api/places/[id]`で本人の履歴を訪問日の新しい順に10件ずつ返します。同日の記録は作成順で並べます。一覧には訪問件数・直近の訪問日と評価だけを返し、感想は含めません。
- 店舗一覧は`status=saved|visited|all`で分類します。旧データも移行せず利用できるよう、取得範囲30件を分類して次のカーソルを返します。該当する店舗がないページにもカーソルがあれば続けて遅延読み込みし、更新時は読み込み済みの範囲を維持します。
- 訪問操作は本人のIDトークンから所有者を決定し、常に非公開です。追加は操作ごとのUUIDで再送による二重登録を防ぎ、編集・削除は更新時刻を照合して別画面の更新を上書きしません。Firestoreへの直接アクセスは禁止です。
- 試作版では履歴を保存店舗ドキュメント内に保持し、1店舗100回を上限とします。感想の長さとの組み合わせでドキュメントの容量超過を避け、`visits`はインデックス対象から除外します。店舗統合時には履歴と直近の評価も引き継ぎます。上限超過・ID衝突で安全に統合できない場合は、元の記録を残します。
- ごみ箱からの復元時にも履歴を保持します。ごみ箱では履歴を閲覧できますが変更はできません。30日の期限後はAPIからアクセスできず、TTLで店舗と一緒に削除します。期限後の再登録は履歴なしで作成します。
- 非公開の保存・評価も将来のユーザー横断レコメンドに利用する方針です。今回は推薦計算や公開レビュー、写真の添付は追加していません。

## ユーザー横断のおすすめ

- ホームの「おすすめ」に、保存・最新評価の共通度を使った候補を10件ずつ表示します。共通の肯定的な保存が2店舗以上あるユーザーを類似ユーザーとし、そのうち3人以上が支持する候補に「保存・評価の傾向が近い人から」と表示します。星2以下は支持とせず、星4以上は加点し、同じ人の再訪で重みを増やしません。
- データが足りない場合は本人の保存ジャンルや集計上の人気を使い、類似ユーザーの推薦とは区別します。候補がなければ不足の案内を表示します。おすすめ設定で全国・都道府県・市区町村を選んで絞り込めます。距離・予算での絞り込みは未対応です。
- 表示情報は共通店舗のJSON-LDで確認した店名・住所・ジャンル・公開URLのみです。除外サイト・SNSや旧AI抽出の共通店舗、他人の手入力・メモ・感想・評価明細・UIDは返しません。本人が手入力したジャンルは好みの補完に使えますが、共通店舗IDを持たない店は協調推薦の対象になりません。
- 非公開の保存・評価も計算に使うことをホーム・おすすめ設定・訪問記録に明示します。誰が保存・評価したかや人数は表示しません。保存済み・訪問済み・ごみ箱・「興味なし」の候補を除外し、「興味なし」はおすすめ設定／アカウント設定から解除できます。
- おすすめ欄が画面に近づくと初回取得し、追加取得は「おすすめをもっと見る」で行います。定期ポーリングは行いません。おすすめから保存すると、他人の追記を引き継がず本人の非公開マイリストに追加し、画面にも反映します。URL・共通店舗IDの重複を確認します。
- APIは `GET /api/recommendations`（`cursor`で追加取得、`dismissed=1`で興味なし一覧）、`POST /api/recommendations`（`action: save | dismiss | restore`と共通店舗ID）です。Firebaseの認証・失効確認、本人の所有権、既存の書き込み上限を適用します。Firestoreへの直接アクセスは拒否します。
- 集計と本人別の候補は基本24時間キャッシュし、最初のアクセス時に更新します。保存・興味なしは次の取得時に除外します。他ユーザーの変更は原則次回の集計に反映するため、即時反映ではありません。外部AIや新しい有料検索サービスは使いません。読み取り・サイズの上限がある試作のため、大規模なデータではすべての記録を計算できません。

- 試作の集計は保存記録20,000件、共通店舗5,000件、推薦候補1,000件までを対象にし、本人別の候補は最大100件とする。全体集計の作り直しはロックで重複を防ぐ。通常の取得でも本人の保存・興味なしを全件読むため、利用量に応じた読み取り監視が必要。

## おすすめの利用エリア

- おすすめ欄の「エリアを変更」、または「おすすめ設定」で全国・都道府県全域・市区町村（政令市の区も含む）を選択します。設定は本人のアカウントに保存し、旅行先などへいつでも変更できます。未設定は全国で、設定は必須ではありません。
- 「現在地から設定」を押したときだけブラウザーに位置の許可を求め、座標を小数3桁（約100m）に丸めて国土地理院の逆ジオコーダーへ送信します。自社APIに座標を送らず、地域候補を表示し、本人が確認して保存します。位置を取得できない・国内の地域を判定できない場合は手動選択に進めます。外部サービスの停止時も手動選択は利用できます。
- 保存先は `users/{uid}/preferences/area`。地域コードと更新日時だけを保持し、精密な座標や位置の履歴は保存しません。APIは `GET/PATCH /api/preferences/area`、認証必須。全国へ戻すと設定ドキュメントを削除します。
- 共通店舗の住所を地域に照合して推薦を絞ります。地域指定時に住所を判定できない店舗は除外し、候補不足なら利用者が都道府県全域・全国へ広げられます。自動では広げません。地域変更時に本人の推薦キャッシュを更新し、以前の地域のカーソルを使い回しません。
- 市区町村データは[国土地理院 muni.js](https://maps.gsi.go.jp/js/muni.js)（2026-10-18取得、1,919件）を加工し、`src/lib/areas/municipalities.json` に同梱しています。先頭ゼロを補い、市と区の間の空白を除去しています。[国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)に従い画面にも出典を表示します。行政区の変更時はこの一覧を更新します。


## 同じURLの入力補助と登録のお祝い

同じ正規化URLを別ユーザーが登録すると、`urlFacts/{URLのSHA-256}`の店名・住所・ジャンルを初期値に使います。編集で実際に変更した空でない項目だけを蓄積します。メモ・訪問・星評価・UID・他のURLはコピーせず、他ユーザーの既存記録も変更しません。除外サイトに外部アクセスする処理はありません。手入力による入力補助と、JSON-LDで検証済みの推薦対象の共通店舗は別管理です。

`GET /api/milestones`は本人のごみ箱以外の保存件数と未表示の最大閾値を返します。5・10・20・50・100件、以後100件ごとにお祝いを表示し、閉じる操作で`POST /api/milestones`へ閾値を送ります。`users/{uid}/milestones/state`に閉じた最大閾値を残し、再読み込みや重複保存で同じ段階を繰り返しません。件数はFirestoreのcount集計を使い、ページ送りや検索件数に依存しません。

既存データの入力補助への移行（管理者用）：

```sh
# 既定はdry-run。プロジェクトtsugikokoのADC認証が必要。
node --conditions=react-server --import tsx scripts/backfill-url-facts.mts
# dry-runで対象件数・上限を確認後に適用
node --conditions=react-server --import tsx scripts/backfill-url-facts.mts --apply --max-records=20000 --max-writes=1000
```

スクリプトは対象の保存記録を読むだけで、書くのは`urlFacts`だけです。ログは件数のみです。`truncated`がtrueの場合は全件を調べられていないため、上限を見直してから実行します。既存の共通情報が新しければ保持し、同じ内容の再実行では書き込みません。

## 利用状況の計測（GA4・BigQuery）

GA4はページの利用状況、BigQueryはサービス側の件数集計に使用します。両者は別の仕組みで、GA4のイベントをBigQueryへエクスポートする設定ではありません。

### GA4の設定

1. Google Analyticsでプロパティと、`https://tsugikoko.com`を対象としたウェブデータストリームを作成します。
2. ウェブストリームの「拡張計測機能」を無効にします。履歴変更による自動ページビュー、離脱クリック、サイト内検索、フォーム操作、ダウンロード等を自動計測しない設定が必須です。`send_page_view: false`だけでは履歴変更の自動計測を止められません。[Google公式の手動ページビュー設定](https://developers.google.com/analytics/devguides/collection/ga4/views)
3. 測定ID（`G-...`）を`apphosting.yaml`の`NEXT_PUBLIC_GA_MEASUREMENT_ID`へ設定し、BUILD/RUNTIMEの両方へ渡します。これは公開用のIDです。値はビルドに埋め込まれるため、変更時は再ビルド・デプロイが必要です。空・形式不正の間はタグを読み込まず、GAへの通信もしません。
4. 本番のRealtimeレポートでページ閲覧を確認します。GA4側にイベント作成ルールや追加タグを設定して、自動計測を再開しないでください。

画面側は`src/lib/analytics.ts`と`src/components/analytics/`です。自動ページビューを無効にし、`/`・`/login`・`/home`へのページ遷移ごとに`page_view`を手動送信します。同じページでの再描画、クエリ・ハッシュだけの変更では追加しません。送信先のページURLは固定の公開ドメインとパスから作り、タイトルも固定値です。流入情報は最初の`page_view`だけに付け、以後のページ閲覧・操作イベントやグローバル設定には残しません。新規登録はFirebaseの`getAdditionalUserInfo(result).isNewUser`を確認して`sign_up`を送り、認証方法名だけを追加します。再ログイン・認証方法の連携・ログイン状態の復元では送信しません。

流入計測は`utm_source`・`utm_medium`・`utm_campaign`・`utm_content`・`utm_term`と`gclid`だけを許可します。UTM値は英字で始まる1〜64文字の英数字・`_`・`-`に限り、電話番号のような7桁以上の数字列（区切りを含む）は除外します。自由文・日本語・メール・URL・二重エンコード・空値・重複キー・上限超過は送りません。UTMには`google`、`cpc`、`autumn_2026`など広告運用用の識別名だけを設定し、人名・メール・ユーザー入力を設定しないでください。英字の人名と広告名は文字種検査だけでは区別できません。`gclid`は英字を含む1〜256文字の英数字・`_`・`-`に限ります。Google広告の自動タグで付くクリック識別子をGA4でも読めるよう残します。AWタグの設置だけではGA4のキャンペーン情報を代替できません。広告管理画面の自動タグ設定やGA4とのリンクは今回のコード変更とは別です。[Google公式の自動タグ説明](https://support.google.com/analytics/answer/10723132?hl=ja)

外部参照元はHTTP(S)のorigin（スキーム・ホスト・ポート、最大255文字）だけを送り、パス・クエリ・認証情報は除外します。自サイト内の遷移では空です。重複を防ぐため`sessionStorage`に最終計測時刻だけを保存し、同じタブで30分間イベントがなければ次のページ読み込みを新しい訪問の入口とします。GA4自身のセッションIDとは独立した送信制御です。リロード・SPA遷移では流入情報を再送せず、保存領域が使えない場合と停止から再開した画面では流入情報を送りません。

操作イベントは`cta_click`（`button_id`: `header_login`、`header_signup`、`hero_save`、`hero_signup_no_url`、`scene_signup`、`recommendation_signup`、`footer_signup`、`menu_signup`、`login_mode_signup`、`login_mode_login`）、`login_start`（`method`、`button_location`: `landing_dialog`または`login_page`、`auth_mode`: `login`または`signup`）、`scroll_depth`（`percent_scrolled`: 25・50・75・90）です。`hero_save`は入力が不正でも送る操作の記録、`hero_signup_no_url`はヒーローの「URLなしではじめる」の操作、`login_start`は認証開始であり認証成功ではありません。スクロールはトップページで画面下端が各割合に達したときに1回ずつ送り、初期表示だけでは送りません。パラメーターは固定値で、フォーム入力・ボタンの表示文言・保存URLは送りません。拡張計測の自動スクロールは無効のままにします。

ユーザーID・氏名・メール・店舗URL・メモ・評価・サイト内検索語・位置情報を計測イベントへ明示的に渡しません。Googleシグナルと広告のパーソナライズも無効です。GAはCookie等の識別子や端末情報を扱い、接続先にはIPアドレスも伝わるため、「個人を識別する情報が一切外部へ送られない」とは説明しません。[Googleのプライバシー設定](https://developers.google.com/tag-platform/security/guides/privacy)

ログイン前は「プライバシーについて」、ログイン後は「アカウント」→「利用状況の集計・アクセス解析」から、このブラウザーの計測を停止できます。設定は`localStorage`へ保存し、停止中はGoogleの無効化フラグとアプリ側の送信抑止を適用します。停止済みでページを開くとGA4を初期化せず、流入情報・操作も送りません。既存のGoogle広告タグはこの設定とは独立しています。設定を保存・参照できない環境も計測を止めます。タグのブロックや通信失敗はログイン・店舗保存を妨げません。BigQueryの件数集計はこのブラウザー設定とは別です。

### BigQueryの日次集計

Cloud Schedulerから認証付き内部API `/api/internal/metrics` を毎日0時台（日本時間）に呼び、前日の日付をキーに`analytics.daily_metrics`へ保存します。呼び出し元はOIDCトークンの宛先・メールアドレスを検証します。同じ日付の再実行はMERGEで置き換えます。

| 項目 | 集計の意味 |
| --- | --- |
| `total_users` / `new_users` | 現存する認証ユーザーのうち、対象日末までの登録数／対象日の登録数 |
| `active_users_7d` / `active_users_30d` | 認証情報の最終更新時刻（なければ最終ログイン時刻）を使った直近の利用者数 |
| `users_with_places` / `saved_places` | 集計時点でごみ箱以外の保存記録を持つ人数／保存件数 |
| `new_saved_places` | 対象日に作成された現存の保存記録数（ごみ箱に移したものも含む） |
| `visited_places` / `total_visits` | ごみ箱以外の訪問済み保存記録数／訪問回数の合計 |
| `date` / `generated_at` / `truncated` | 対象日／集計時刻／読み取り上限到達の有無 |

認証情報と保存記録をそれぞれ最大50,000件読み、上限に達した場合は`truncated`で示します。店舗URL、ユーザーID、メール、メモ、評価明細はBigQueryへ送りません。集計用にサーバー内で参照する情報と、BigQueryへ書く件数を区別します。

削除済みユーザーや消去済み記録を復元するイベントログは持たないため、これは厳密な過去日のスナップショットではありません。アクティブ数には日付境界から集計時点までの認証更新も入り、GA4のアクティブユーザー数とは定義が異なります。同日分を後で再実行すると、現存データの変化により結果が変わる場合があります。

`METRICS_ENABLED`、`METRICS_DATASET`、`METRICS_INVOKER`、`METRICS_URL`をサーバーへ設定します。BigQueryデータセット、呼び出し用サービスアカウント、権限、Schedulerの作成・有効化は別途必要です。日次走査のFirestore読み取りとBigQuery・Schedulerの費用を監視してください。

### 画面からの退会

「アカウント → 退会・データ削除」で削除範囲を表示し、連携済みプロバイダーで再認証した後に確認チェックと実行ボタンを表示します。`POST /api/account/deletion` は失効確認済みIDトークンの `auth_time` が5分以内であることと、固定の確認値を検証します。対象UIDはトークンから決定し、リクエスト本文のUID等の追加項目は拒否します。

Cloud Tasksに先にジョブを登録し、成功後に `accountDeletions/{uid}` へ受付IDと時刻を保存します。その後Authを停止・失効し、クライアントはログアウトして受付案内へ移動します。キュー登録失敗時にはアカウントを停止しません。停止が一時的に失敗した場合もジョブが再開し、停止から5分以上待って削除します。キュー登録後に受付保存が失敗したジョブは、受付IDの照合で無視します。受付案内は完了通知ではありません。

専用キュー `projects/tsugikoko/locations/asia-east1/queues/account-deletion` は同時実行1、最大試行100、再試行期間86400秒、バックオフ30〜3600秒で設定しています。実行開始は登録から6分後。`apphosting.yaml` の `ACCOUNT_DELETION_ENABLED/QUEUE/INVOKER/URL` を使用します。App Hosting実行用サービスアカウントにこのキューへの `roles/cloudtasks.enqueuer` を付与し、既存の呼び出し用サービスアカウントを利用します。Authの更新・削除権限は既存の `roles/firebase.sdkAdminServiceAgent` に含まれます。

内部の `POST /api/internal/account-deletion` は指定サービスアカウントと宛先に一致するOIDCトークンだけを受け付けます。処理途中の失敗はキューが再試行します。ログの `account_deletion_task_failed` と `account_deletion_prepare_pending`、キューの失敗・滞留、古い `accountDeletions` を運用時に確認してください。再試行で解消しない受付は、下記CLIで状態を確認して同じUIDの削除を再開します。キューの再試行期限を過ぎても受付記録と停止状態は残ります。

エミュレーターでは外部キューへ接続せず、統合テストからワーカー関数を直接実行します。ブラウザーE2Eは受付まで、統合テストは実データ消去・失敗と再開・他人の記録保持を検証します。本番用キューと権限は作成済みですが、画面とAPIはこの変更のデプロイ後に有効になります。

### メールによるデータ削除の受付・実行

1. 受付メールから対象アカウント・希望範囲を確認し、Firebase Authenticationで対象を特定します。申告されたメールやUIDだけで削除せず、既存の登録メール宛の確認と返信等で本人確認します。メール提供のないアカウントやログイン不能の場合は、利用中のログインサービスによる本人確認などを個別に案内し、確認できるまで実行しません。パスワード・認証コード・トークンをメールで受け取らないでください。
2. アカウント全体を削除すると、連携済みの全ログイン方法と保存リストが対象になり、復元できないことを本人に確認します。Facebook連携だけの解除や特定データの訂正・削除に、下記の全件削除コマンドを使わないでください。
3. 本人確認後、原則30日以内を目安に対応します。期限内に対応できない場合は理由と見込みを連絡します。受付・本人確認・削除範囲の合意・実行日・完了連絡をアクセス制限した受付記録に残し、不要な本人情報は保持しません。
4. 必ず以下のプレビューを確認し、運営者が対象UIDを照合してから停止・削除を実行します。管理ツールはApplication Default Credentialsの権限で実行し、ブラウザーや公開APIには出しません。本番では更新済みのおすすめ処理をデプロイしてから使います。

```sh
# UIDはFirebase Authenticationで本人確認した対象のものを使う。まず参照のみ。
node --conditions=react-server --import tsx scripts/delete-account.mts --project=tsugikoko --uid=対象UID

# 本人確認・全件削除の合意が取れたアカウントを停止し、セッションを失効させる。
node --conditions=react-server --import tsx scripts/delete-account.mts --project=tsugikoko --uid=対象UID --prepare --confirm=対象UID --identity-verified

# 5分以上待ち、進行中の処理が終了した後で削除する。
```

`--prepare`でAuthを無効化・失効させ、`accountDeletions/{uid}`に停止開始時刻を保存します（画面受付のID・受付時刻がある場合は保持します）。`--delete`は5分経過と停止状態を検証し、`users/{uid}`を子コレクションも含めて再帰的に削除し、Authのユーザーを削除します。保存・ごみ箱・訪問履歴・メモ・地域設定・興味なし・節目の表示履歴・重複防止用キーが対象です。派生する全体のおすすめモデルと再生成可能なおすすめキャッシュも消します。他の利用者の保存記録・認証情報は削除しません。

削除中だけおすすめの再集計を停止します。処理途中で失敗した場合はアカウント停止・おすすめの保守状態・再開用の記録が残ります。原因を解消して同じUIDの `--delete` を再実行してください。おすすめのロックだけを手動で消して処理を放置しないでください。Auth削除後に中断しても、再開用の記録から処理できます。完了するとロック・再開用の記録も削除します。

完了後にプレビューを再実行して `authExists: false`、`savedPlaces: 0`、`collections: []`、`prepared: false` を確認し、対象者へ連絡します。調査・削除の出力は件数・状態のみで、メールアドレス・トークン・個人メモは出しません。コマンドラインのUIDは運営用情報として扱ってください。

残る情報：個人と結び付かないBigQueryの件数集計、入力者との対応を持たない共通店舗・URL情報、外部サービスのログやバックアップはこのツールでは削除しません。店舗共通情報に個人情報が誤入力されている等の申告があれば、別途対象を調べて対応します。GA4・広告はFirebase UIDを送っていないため、アカウント削除だけでCookie等に基づく外部データの削除が完了したとは回答しません。ログやバックアップの照会・削除が必要な場合はGoogle側の保存設定・手順を確認します。

### Foursquare OS Places の入力補助（恵比寿周辺で有効）

GoogleマップのURLを保存すると、機能が有効な場合は編集画面を開く。リンクの店舗名とピン座標（表示中心の `@` は使わない）を地域カタログと照合し、候補が1件かつ報告・更新時期の問題がなければ空欄へ店名・住所・ジャンルを入れる。支店名の片側欠落は警告する。複数候補や未確認の報告、1年以上更新のない情報は自動入力せず、本人が候補を選ぶ。いずれも「変更を保存」で確定し、入力済み・入力操作中の項目は上書きしない。Google API の表示用データは使用しない。100m以内・名前一致/支店名差分という暫定条件であり、完全自動の店舗同定を保証しない。IDのみ・店舗ピンなしのURL、地域カタログ外、候補のない店舗は手入力できる。

実行中に Foursquare の Iceberg を検索せず、サーバー内の地域データを検索する。手元の実データは恵比寿周辺のみ（2026-10-30取得、2,321行から飲食店等780行）。全国対応ではない。準備途中の実データは `.local-data/` に置く。公開用の780行は `data/foursquare/ebisu-2026-10-30.json` に固定し、NOTICE/ライセンスと一緒にバージョン管理する。公開ディレクトリへは置かない。Foursquareのトークンはアプリに渡さない。準備コマンドは出力を上書きせず、切り詰めたエクスポート・不明な出典・重複ID・50MB超を拒否する。

```sh
node --import tsx scripts/prepare-foursquare.mts input.json .local-data/foursquare.json
FOURSQUARE_ENABLED=true FOURSQUARE_CATALOG_PATH=.local-data/foursquare.json npm run dev
```

入力JSONは Foursquare OS Places のエクスポートを `{ "source": "Foursquare OS Places (Apache-2.0)", "truncated": false, "rows": [...] }` で包む。日本の飲食カテゴリのみ採用し、閉店日あり・店名/住所等の不足を除く。`unresolved_flags` と `date_refreshed` は候補の警告に使用する。閉店日なしや最終更新日は営業中・全情報の正確性を保証しない。ジャンルはカテゴリの明示語だけから判定し、不明なら未設定とする。スナップショットは最大10万行・50MB、拡大時には分割・索引・更新運用を別途整備する。本番ではapphosting.yamlのBUILD/RUNTIME両方で有効化・カタログのパスを指定する。next.config.tsがファイルと版数ハッシュを確認し、欠落・破損時はビルドを止める。outputFileTracingIncludesでサーバーの配布物へ含める。対象は恵比寿周辺のみ。

保存はサーバーが候補ID・カタログ版数・本人の記録・更新版数を検証する。出典、項目ごとの元の値/取り込み値を `foursquareSource` に保持する。取り込んだ記録は `foursquareImported` で識別し、後の手修正も含め `urlFacts` への転記・バックフィル対象から除く。共通店舗への登録やおすすめへの公開は行わない。画面と共有文に情報提供元を表示する。[NOTICE](public/licenses/foursquare-NOTICE.txt) と [Apache License 2.0](public/licenses/Apache-2.0.txt) を配布物に含める。住所の結合・ジャンルの変換・地域/カテゴリの選別はNOTICEに明記した。

停止は `FOURSQUARE_ENABLED=false` で行う。停止後も各記録の「入力補助で取り込んだ情報を元に戻す」は使用でき、取り込んだままの項目だけを元に戻す。本人が後から変更した値、メモ、訪問履歴、リストは維持する。一括撤回は次のコマンドで、既定は件数確認のみ。実行には運営者のデータアクセス権が必要。2万件を超える場合は変更せず停止する。競合があれば終了コード2で通知するので再確認する。

```sh
node --conditions=react-server --import tsx scripts/withdraw-foursquare.mts
# 件数を確認し、公開停止・撤回の指示を受けてから適用
node --conditions=react-server --import tsx scripts/withdraw-foursquare.mts --apply
```

藤田さんの方針によりGoogleへの問い合わせを実装の前提にはしない。URL由来の情報による照合の許諾を確認済みとは扱わない。連携停止と、出典を追った撤回ができる構成にする。2026-10-31に藤田さんからcommit・push・deployの指示を受け、恵比寿周辺で有効化する。既存の保存記録を一括で変更する処理は行わない。

保存時の候補再確認は、PATCH全体の更新制限を使い、候補表示の分10回枠を二重消費しない。再確認の障害・停止時には「候補の入力を取り消して手入力に戻る」で、自動入力したままの値だけを取り消し、本人が入力した項目とメモを保持して保存し直せる。何も取り込んでいなければ `foursquareImported` は付けない。一度取り込んだ記録は、撤回後も共通情報への転記対象には戻さない。

検証: `E2E_AUTH_EMULATOR=1 E2E_FOURSQUARE=1 npx playwright test --workers=1` を認証・Firestoreエミュレーター内で実行すると、架空の地域カタログを用いてスマホ/PCの入力・保存・撤回・遅延応答・失敗時の手入力を確認する。実店舗データやFoursquareのトークンはテストで使わない。
