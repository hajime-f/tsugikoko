# ツギココ

気になったら、ツギココ。

飲食店・カフェの「行きたい」を記録するWebサービスです。仕様・技術スタック・設計方針は[CONTEXT.md](CONTEXT.md)を参照してください。

## 開発環境

Node.js 22系とnpmを使用します。App Hostingのビルド環境も22系に指定しています。

```sh
npm install
npm run dev
```

http://127.0.0.1:3000 を開きます。

この開発環境のTurbopackの起動制限を避けるため、開発・本番ビルドにはNext.jsのWebpackオプションを使用しています。

## 現在の実装

- スマートフォン中心のログイン前トップページ
- Firebase AuthenticationによるGoogle・Xの登録・ログイン・ログアウト
- URLからの店舗登録、非公開マイリスト、店名・住所・メモの編集、30日間のごみ箱
- 公式サイトなどの構造化データ（JSON-LD）からの店名・住所・料理ジャンルの自動入力。取得できない場合は手入力
- 非公開の訪問記録（訪問日・任意の星1〜5・任意の感想）、再訪履歴、記録の編集・削除
- ログイン状態の維持と未ログイン時の`/home`から`/login`への移動
- スマートフォン中心のログイン後ホーム（マイリスト・ユーザー横断のおすすめ）
- アカウント表示、認証方法の追加・解除（最後の方法は解除不可）
- URL入力の検証と、ログイン完了後のマイリストへの自動保存
- 保存操作を試せる画面内デモ
- モバイルメニュー、FAQ、プライバシー説明、画像クレジット

Google・X認証と店舗保存は実際のFirebaseに接続します。訪問記録・評価と、ユーザー横断のレコメンドを利用できます。ログイン前にURLを入力して「保存してはじめる」を押すと、ログイン完了後にFirestoreへ非公開で自動保存します。URLは保存成功まで`sessionStorage`でログインしたユーザーにひも付けて保持し、失敗時は入力欄から再試行できます。再読み込みや同じURLの再試行でも、サーバーで重複を防ぎます。未保存のURLはログアウト時に消去しますが、登録済みの店舗はログアウト後も残ります。試作中は検索エンジン向けにnoindexを指定しています。

## 認証設定

- `src/lib/firebase/client.ts`はWebアプリの公開設定です。サービスアカウント鍵やOAuthシークレットは含みません。
- Google認証の設定は`firebase.json`で管理し、`firebase deploy --only auth --project tsugikoko`で反映します。
- Firebase Authenticationの承認済みドメインに、公開ドメイン・`localhost`・`127.0.0.1`を設定済みです。同一メールアドレスで複数アカウントを作成する設定は無効です。
- 認証はFirebase SDKのポップアップを利用します。閉じた場合・ブロック・通信失敗は画面内で案内します。SNS内ブラウザではSafari/Chromeで開き直してください。
- 初回認証はアカウント登録を兼ねます。既存ユーザーには以前と同じ方法を選ぶよう案内し、新しい方法はログイン後に`linkWithPopup`で同一UIDへ連携します。メールアドレスや表示名だけで独自に統合しません。
- Xのログイン・既存アカウントへの連携を有効化しています。Facebook・Appleも処理は実装済みですが、外部設定が未完了なので「準備中」と表示します。

### X・Facebook・Appleの設定手順

アプリには3つの認証・既存アカウントへの連携処理があります。2026年10月19日時点でGoogleとXはFirebase側の設定を確認し、本番で有効化しています。Facebook・Appleは外部設定が済むまで「準備中」と表示します。

共通して使う値：

| 項目 | 値 |
| --- | --- |
| サイトURL | `https://tsugikoko.com` |
| コールバック／リダイレクト／Return URL | `https://tsugikoko.firebaseapp.com/__/auth/handler` |
| Firebaseプロジェクト | `tsugikoko` |
| Firebase認証設定 | [Authentication → ログイン方法](https://console.firebase.google.com/project/tsugikoko/authentication/providers) |

X：

現時点の確認：FirebaseのTwitterプロバイダーとキー登録、承認済みドメインは確認済みです。ただし本番の認証開始はXから`401 / code 32 / Could not authenticate you`が返るため、OAuth 1.0a設定とAPI Key・API Key Secretの組み合わせを再確認する必要があります。アプリ側の登録・再ログイン・連携・解除はエミュレーターで検証済みですが、本番のXログイン完了は未確認です。

1. [X Developer Console](https://console.x.com/)で開発者アカウントとアプリを作成し、ユーザー認証（OAuth 1.0a）を設定します。Firebaseでは表示名が引き続き「Twitter」の場合があります。
2. アプリのコールバックURLとサイトURLに上表の値を指定します。投稿の権限は必要ありません。
3. API KeyとAPI Key Secretを発行し、Firebaseの「Twitter」に入力して有効化・保存します。OAuth 2.0のClient IDやBearer Tokenではありません。
4. 開発者登録・利用プランの条件はXの申込画面で確認してください。有料契約はこの実装作業では行いません。[Firebase公式手順](https://firebase.google.com/docs/auth/web/twitter-login)

Facebook：

1. [Meta for Developers](https://developers.facebook.com/apps/)でアプリを作成し、Facebook LoginのWeb認証を追加します。
2. Facebook Login設定の「有効なOAuthリダイレクトURI」に上表のコールバックURLを指定します。
3. アプリのApp IDとApp Secretを、Firebaseの「Facebook」に入力して有効化・保存します。
4. まずアプリの管理者・テスターで試します。一般利用者に開放する際は、Metaの管理画面が求める公開設定・プライバシーポリシー・データ削除案内等を整えます。開発モードのテスト成功だけで一般公開済みとは判断しません。[Firebase公式手順](https://firebase.google.com/docs/auth/web/facebook-login)

Apple：

1. [Apple Developer](https://developer.apple.com/account/)にログインします。Sign in with Appleの設定にはApple Developer Programへの参加が必要です。未加入なら、加入条件・費用を確認してから本人が手続きします。
2. Certificates, Identifiers & ProfilesでSign in with Appleを有効にしたApp IDを用意し、Web用のServices IDを登録して、そのApp IDに関連付けます。
3. Web設定のドメインに`tsugikoko.firebaseapp.com`、Return URLに上表のコールバックURLを指定します。Services IDはFirebaseへ入力するため控えます。
4. Sign in with Apple用の秘密鍵を作成し、Key IDと`.p8`ファイルを安全に保管します。Team IDも控えます。
5. Firebaseの「Apple」にServices ID、Team ID、Key ID、秘密鍵を入力して有効化・保存します。[Firebase公式手順](https://firebase.google.com/docs/auth/web/apple)、[AppleのWeb設定手順](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/)

最後にツギココ側を有効化：

1. 設定が終わったサービス名を知らせてください。鍵やシークレットをチャット・Git・`NEXT_PUBLIC_*`変数へ貼り付ける必要はありません。
2. 実装担当はFirebase側の有効状態を確認し、`apphosting.yaml`の`NEXT_PUBLIC_AUTH_PROVIDERS`へ設定済みIDだけを追加してデプロイします。例：`google.com,twitter.com,facebook.com,apple.com`。一部だけ完了なら、その方法だけ追加できます。ローカルは`.env.local`へ同じ値を設定します。
3. 本番の別ブラウザでログイン・再読込・ログアウトを確認します。Googleで登録済みの人は、Googleでログインして「アカウント」から追加すると、同じ保存リストを使えます。各方法のメールアドレスが異なる場合に、同一人物を自動推測して統合することはありません。
4. Firebaseの「承認済みドメイン」に本番ホストがあることも確認します。SNS内ブラウザでポップアップが開けない場合はSafariやChromeで開き直します。

`/home`の表示制御に加え、店舗APIはFirebase Admin SDKでIDトークンと失効を検証します。所有者はトークンのUIDから決定し、入力からは受け取りません。Firestore Rulesでクライアントからの直接アクセスを拒否し、個人データは認証済みAPIだけで扱います。応答は`private, no-store`です。

## 独自ドメインとSNS共有

公開URLは`https://tsugikoko.com`です。`src/lib/site.ts`で管理し、トップページのcanonical・OGPに使用します。認証用の`authDomain`とコールバックは`tsugikoko.firebaseapp.com`を維持し、Cloud Tasksの内部配送先は`hosted.app`のままにします。Firebaseの承認済みドメインには`tsugikoko.com`と`www.tsugikoko.com`を登録済みです。旧ドメインから移動した際は、ブラウザのログイン状態がドメインごとに保存されるため再ログインしてください。

マイリスト・おすすめカードの「共有」から投稿内容を確認し、X・LINEの投稿画面へ進めます。対応端末では標準の共有メニューも利用でき、投稿文のコピーにも対応します。共有するのは店名と元ページのURLだけで、メモ・訪問記録・評価・UIDは含めません。記録の公開設定は変更しません。SNSへの最終送信は本人が各SNSで行い、投稿APIや投稿用アクセストークンは利用しません。XでのログインとXへの共有は別の機能で、共有にはツギココへのX連携は必要ありません。

## 店舗登録と自動入力

- `/api/places`で登録と30件単位の一覧取得、`/api/places/[id]`で編集・再取得・ごみ箱・復元を行います。
- カードには「再取得」ボタンを表示しません。店名が未入力の場合だけ「編集」を緑色のボタンで強調し、手入力を案内します。店名の保存後は通常の編集ボタンに戻ります。再取得API（`PATCH`の`retry`）は自動入力の対象URLに限って残しています。
- マイリスト・ごみ箱は先頭30件を表示し、末尾の300px手前までスクロールすると次の30件を自動で読み込みます。追加取得は重複実行を防ぎ、失敗時は表示済みの店舗を残して末尾から再試行できます。「もっと見る」は手動操作・自動読み込み非対応環境用にも残します。通常一覧の定期更新・画面への復帰・編集後も読み込み済みのページ数を維持し、タブや検索条件を切り替える前の古い応答は反映しません。
- マイリストは店名・住所・自分用メモの部分一致検索、ジャンル（未設定を含む）の絞り込み、登録が新しい順／店名順の並べ替えに対応します。行きたい／訪問済み／ごみ箱と組み合わせ、未読込の記録も対象にします。検索は入力確定後に検索ボタンで実行し、空白区切りの語はAND、全角半角と英字の大小を正規化します。条件変更では先頭30件に戻り、その後は遅延取得します。新規URLの保存後は条件を解除して一覧へ戻します。
- `GET /api/places` の追加パラメーターは `q`（100文字以内）、`genre`（`all`／`unset`／ジャンルID）、`sort`（`newest`／`name`）です。店名順は日本語の照合順で、ふりがな順ではありません。未入力の店名は末尾、同名は登録日時とIDで順序を固定します。
- 試作の検索・ジャンル絞り込み・店名順は、リクエストごとに本人の通常記録またはごみ箱を全件読み、サーバーで絞り込みます。300件保存していれば1ページの取得でも300件分を読みます。追加の検索サービスは使いません。読み取りを抑えるため、条件が有効な間は定期ポーリングと画面復帰時の自動更新を止め、検索ボタンの再実行・編集後などで更新します。通常一覧は従来どおり30件単位です。利用増加時には検索用インデックスやキャッシュを検討します。
- 店舗カードの上部には、判定できた料理ジャンルに対応する共通のイメージ写真を表示します。ジャンルが不明な場合は、店舗IDごとに固定した4色の淡い背景と装飾アイコンを表示します。不明ジャンルの装飾はCSS・SVGで描画します。一覧の見出し・検索欄・絞り込み・タブ・追加操作は固定せず、ページと一緒にスクロールします。装飾の色・アイコンは店舗のジャンルや評価を表しません。
- `users/{uid}/savedPlaces`に本人の記録、`places`に確認済みの共通店舗情報、`placeSources`に取得元と1日分の再利用情報を分けます。本人が入力した店名・住所・ジャンルは、`urlFacts`に必要項目だけを保存し、同じ正規化URLを別ユーザーが登録したときの入力補助に再利用します。メモ・訪問・星評価・UID・追加のURLは再利用しません。
- 同じURLは追跡パラメータを除いて正規化し、トランザクションで重複登録を防ぎます。食べログの口コミ・写真ページ、一休のプランページ、XやInstagramの共有URLも店舗・投稿単位に揃えます。異なる取得元の共通店舗照合は、自動入力できた店名と住所の完全一致を使い、名前だけで支店を統合しません。
- 保存・編集・再取得の合計は、試作時は1ユーザーあたり20回/分・200回/日。再取得は1分間隔、通常の取得結果は1日再利用します。本人による「再取得」では10分より古い結果を使わず元ページを読み直します。取得方式のバージョンが変わった場合は古いキャッシュを使いません。
- URLを先に保存し、本番ではCloud Tasksのジョブで取得を継続します。外部取得は8秒・1.5MBまでとし、リダイレクトを追いません。中断した処理はFirestoreの状態を基に一覧再表示時に最大3回まで再開します。Cloud Tasks無効時は90秒の処理リースが切れれば再開でき、ジョブ登録日時には左右されません。登録から10分間のジョブ再登録待ちはCloud Tasks有効時だけ適用します。
- Cloud Tasksのキュー`place-extraction`（asia-east1）・呼び出し用サービスアカウント・必要な権限を構築し、`PLACE_TASKS_ENABLED=true`に設定しました。内部APIはOIDCで呼び出し元を検証します。ローカル・エミュレーター、または`PLACE_TASKS_ENABLED=false`の環境ではCloud Tasks APIを呼ばず`after`を使い、内部APIは401を返します。無効時はプロセス異常終了からの復旧に一覧の再表示が必要です。
- 自動補完は本人の追記を上書きしません。写真・紹介文・口コミ・OGP画像は保存・表示せず、独自のアイコンを表示します。
- ごみ箱は30日間復元可能です。`purgeAt`のTTLで保存記録を削除し、期限超過した記録はTTLの実行待ちでもAPIから非表示にします。共通店舗情報とURL対応用のハッシュは別管理です。

### 構造化データによる自動入力

- 2026年10月18日に、食べログ・一休がApp Hosting（Google Cloud）からのアクセスに403を返すことを本番のログで確認しました。アクセス制限は回避しない方針のため、URLを登録して店舗情報は手入力する方式に変更し、AI（Gemini）による解析は廃止しました。経緯はCONTEXT.mdに記載しています。
- `src/server/extraction/sources.ts`の除外リスト（食べログ・一休・ぐるなび・ホットペッパーグルメ・Retty・Instagram・X・Facebook・TikTok・YouTube・Googleマップ）に含まれるURLは取得せず、登録時点で`needs_review`・`unsupported`とします。カードには「{サイト名}の気になるお店」と表示し、編集から手入力します。
- それ以外のURLは、取得前に`robots.txt`を確認します。`Tsugikoko`向け、なければ全体向けの規則に従い、取得が禁止されている場合や`robots.txt`が5xxを返す場合は取得しません。404などは制限なしとして扱います。
- 接続前に名前解決したすべてのアドレスを検証し、ローカル・内部ネットワーク・予約済みのアドレスが含まれる場合は接続しません。検証したアドレスへ直接接続し、リダイレクトは追跡しません。
- 401・403・429・451とリダイレクトは取得の拒否として扱い、回避せず`unsupported`とします。その他の取得失敗は`fetch_failed`、JSON-LDで店舗を特定できない場合は`not_found`とし、いずれもURLと個人メモを保持して手入力を案内します。`failed`は内部エラーの場合だけです。
- `src/server/extraction/parser.ts`でJSON-LDの店舗名・住所を解析します。配列・`@graph`・住所の`@id`参照に対応し、複数店舗や不完全な住所を勝手に確定しません。
- 取得のリースは90秒で、古い試行が新しい試行を上書きしないよう識別子を確認します。取得元URL・取得方法・取得日時を共通情報の出典に記録します。取得方式のバージョンは`json-ld-v2`です。
- `npm run test:unit`で除外判定・robots.txt・接続先の検証・JSON-LD解析、`npm run test:extraction`でエミュレーター上の保存・統合、`npm run test:auth`で画面操作を確認できます。エミュレーターテストにはJava 21が必要です。

### ジャンル別のカード画像

- 編集画面でジャンルを1つ選択できます。[一休トップの料理ジャンル](https://restaurant.ikyu.com/)と[料理ジャンル一覧](https://restaurant.ikyu.com/keyword/genre/)を参考に、主要な料理分類・既存分類・ユーザー提供画像に対応する分類を合わせた52種類を6グループで表示します（2026年10月18日確認）。任意入力で「未設定」に戻せます。選択肢は`src/lib/places/genres.ts`の`genreGroups`で管理します。
- 本人が変更したジャンルのみPATCHで送り、変更しなければ送信を省略します。ジャンルが未設定の場合は、従来の背景・装飾を表示します。
- 取り込み時にJSON-LDの`servesCuisine`と飲食店の型を読み、店舗情報欄の「ジャンル」「料理ジャンル」等、店舗名を含むページタイトル、店名の明示的な語を補完に使います。本文中のメニュー紹介や口コミ・ナビゲーション・関連記事は分類根拠にしません。判断できない場合は不明のままにします。
- ジャンルの判定にAIは使いません。ジャンルを収集していない旧キャッシュは、次の取り込み・再取得でページを読み直します。
- 「カフェ」「喫茶店」は「カフェ・喫茶店」（ID `cafe`）に統合しています。旧 `kissaten` の記録・取得キャッシュ・おすすめは読み取り時に `cafe` として扱い、旧画面からの入力や絞り込みにも互換対応しています。写真はカフェの提供画像を使います。
- ホームの挨拶は端末の現地時刻に合わせ、5時〜11時未満は「おはようございます」、11時〜18時未満は「こんにちは」、それ以外は「こんばんは」です。1分ごとと画面に戻ったときに更新します。

### 訪問記録と評価

- カードの「行ってきた」から訪問日、星1〜5（任意）、感想（任意・2,000文字以内）を記録します。日付の初期値は日本時間の今日で、未来日・実在しない日付はサーバーでも拒否します。未評価は`null`として星の値と区別します。
- 1件でも訪問記録がある店舗は「訪問済み」、0件なら「行きたい」に表示します。再訪は別の記録として残し、編集・確認付きの削除ができます。最後の記録を削除すると「行きたい」に戻ります。
- `PATCH /api/places/[id]`の`addVisit`・`editVisit`・`deleteVisit`で更新し、`GET /api/places/[id]`で本人の履歴を訪問日の新しい順に10件ずつ返します。同日の記録は作成順で並べます。一覧には訪問件数・直近の訪問日と評価だけを返し、感想は含めません。
- 店舗一覧は`status=saved|visited|all`で分類します。旧データも移行せず利用できるよう、取得範囲30件を分類して次のカーソルを返します。該当する店舗がないページにもカーソルがあれば続けて遅延読み込みし、更新時は読み込み済みの範囲を維持します。
- 訪問操作は本人のIDトークンから所有者を決定し、常に非公開です。追加は操作ごとのUUIDで再送による二重登録を防ぎ、編集・削除は更新時刻を照合して別画面の更新を上書きしません。Firestoreへの直接アクセスは禁止です。
- 試作版では履歴を保存店舗ドキュメント内に保持し、1店舗100回を上限とします。感想の長さとの組み合わせでドキュメントの容量超過を避け、`visits`はインデックス対象から除外します。店舗統合時には履歴と直近の評価も引き継ぎます。上限超過・ID衝突で安全に統合できない場合は、元の記録を残します。
- ごみ箱からの復元時にも履歴を保持します。ごみ箱では履歴を閲覧できますが変更はできません。30日の期限後はAPIからアクセスできず、TTLで店舗と一緒に削除します。期限後の再登録は履歴なしで作成します。
- 非公開の保存・評価も将来のユーザー横断レコメンドに利用する方針です。今回は推薦計算や公開レビュー、写真の添付は追加していません。

## ユーザー横断のおすすめ

- ホームの「おすすめ」に、保存・最新評価の共通度を使った候補を10件ずつ表示します。共通の肯定的な保存が2店舗以上あるユーザーを類似ユーザーとし、そのうち3人以上が支持する候補に「保存・評価の傾向が近い人から」と表示します。星2以下は支持とせず、星4以上は加点し、同じ人の再訪で重みを増やしません。
- データが足りない場合は本人の保存ジャンルや集計上の人気を使い、類似ユーザーの推薦とは区別します。候補がなければ不足の案内を表示します。おすすめ設定で全国・都道府県・市区町村を選んで絞り込めます。距離・予算での絞り込みは未対応です。
- 表示情報は共通店舗のJSON-LDで確認した店名・住所・ジャンル・公開URLのみです。除外サイト・SNSや旧AI抽出の共通店舗、他人の手入力・メモ・感想・評価明細・UIDは返しません。本人が手入力したジャンルは好みの補完に使えますが、共通店舗IDを持たない店は協調推薦の対象になりません。
- 非公開の保存・評価も計算に使うことをホーム・おすすめ設定・訪問記録に明示します。誰が保存・評価したかや人数は表示しません。保存済み・訪問済み・ごみ箱・「興味なし」の候補を除外し、「興味なし」はおすすめ設定／アカウント設定から解除できます。
- おすすめ欄が画面に近づくと初回取得し、追加取得は「おすすめをもっと見る」で行います。定期ポーリングは行いません。おすすめから保存すると、他人の追記を引き継がず本人の非公開マイリストに追加し、画面にも反映します。URL・共通店舗IDの重複を確認します。
- APIは `GET /api/recommendations`（`cursor`で追加取得、`dismissed=1`で興味なし一覧）、`POST /api/recommendations`（`action: save | dismiss | restore`と共通店舗ID）です。Firebaseの認証・失効確認、本人の所有権、既存の書き込み上限を適用します。Firestoreへの直接アクセスは拒否します。
- 集計と本人別の候補は基本24時間キャッシュし、最初のアクセス時に更新します。保存・興味なしは次の取得時に除外します。他ユーザーの変更は原則次回の集計に反映するため、即時反映ではありません。外部AIや新しい有料検索サービスは使いません。読み取り・サイズの上限がある試作のため、大規模なデータではすべての記録を計算できません。

- 試作の集計は保存記録20,000件、共通店舗5,000件、推薦候補1,000件までを対象にし、本人別の候補は最大100件とする。全体集計の作り直しはロックで重複を防ぐ。通常の取得でも本人の保存・興味なしを全件読むため、利用量に応じた読み取り監視が必要。

## おすすめの利用エリア

- おすすめ欄の「エリアを変更」、または「おすすめ設定」で全国・都道府県全域・市区町村（政令市の区も含む）を選択します。設定は本人のアカウントに保存し、旅行先などへいつでも変更できます。未設定は全国で、設定は必須ではありません。
- 「現在地から設定」を押したときだけブラウザーに位置の許可を求め、座標を小数3桁（約100m）に丸めて国土地理院の逆ジオコーダーへ送信します。自社APIに座標を送らず、地域候補を表示し、本人が確認して保存します。位置を取得できない・国内の地域を判定できない場合は手動選択に進めます。外部サービスの停止時も手動選択は利用できます。
- 保存先は `users/{uid}/preferences/area`。地域コードと更新日時だけを保持し、精密な座標や位置の履歴は保存しません。APIは `GET/PATCH /api/preferences/area`、認証必須。全国へ戻すと設定ドキュメントを削除します。
- 共通店舗の住所を地域に照合して推薦を絞ります。地域指定時に住所を判定できない店舗は除外し、候補不足なら利用者が都道府県全域・全国へ広げられます。自動では広げません。地域変更時に本人の推薦キャッシュを更新し、以前の地域のカーソルを使い回しません。
- 市区町村データは[国土地理院 muni.js](https://maps.gsi.go.jp/js/muni.js)（2026-10-18取得、1,919件）を加工し、`src/lib/areas/municipalities.json` に同梱しています。先頭ゼロを補い、市と区の間の空白を除去しています。[国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)に従い画面にも出典を表示します。行政区の変更時はこの一覧を更新します。


## 同じURLの入力補助と登録のお祝い

同じ正規化URLを別ユーザーが登録すると、`urlFacts/{URLのSHA-256}`の店名・住所・ジャンルを初期値に使います。編集で実際に変更した空でない項目だけを蓄積します。メモ・訪問・星評価・UID・他のURLはコピーせず、他ユーザーの既存記録も変更しません。除外サイトに外部アクセスする処理はありません。手入力による入力補助と、JSON-LDで検証済みの推薦対象の共通店舗は別管理です。

`GET /api/milestones`は本人のごみ箱以外の保存件数と未表示の最大閾値を返します。5・10・20・50・100件、以後100件ごとにお祝いを表示し、閉じる操作で`POST /api/milestones`へ閾値を送ります。`users/{uid}/milestones/state`に閉じた最大閾値を残し、再読み込みや重複保存で同じ段階を繰り返しません。件数はFirestoreのcount集計を使い、ページ送りや検索件数に依存しません。

既存データの入力補助への移行（管理者用）：

```sh
# 既定はdry-run。プロジェクトtsugikokoのADC認証が必要。
node --conditions=react-server --import tsx scripts/backfill-url-facts.mts
# dry-runで対象件数・上限を確認後に適用
node --conditions=react-server --import tsx scripts/backfill-url-facts.mts --apply --max-records=20000 --max-writes=1000
```

スクリプトは対象の保存記録を読むだけで、書くのは`urlFacts`だけです。ログは件数のみです。`truncated`がtrueの場合は全件を調べられていないため、上限を見直してから実行します。既存の共通情報が新しければ保持し、同じ内容の再実行では書き込みません。

## 利用状況の計測（GA4・BigQuery）

GA4はページの利用状況、BigQueryはサービス側の件数集計に使用します。両者は別の仕組みで、GA4のイベントをBigQueryへエクスポートする設定ではありません。

### GA4の設定

1. Google Analyticsでプロパティと、`https://tsugikoko.com`を対象としたウェブデータストリームを作成します。
2. ウェブストリームの「拡張計測機能」を無効にします。履歴変更による自動ページビュー、離脱クリック、サイト内検索、フォーム操作、ダウンロード等を自動計測しない設定が必須です。`send_page_view: false`だけでは履歴変更の自動計測を止められません。[Google公式の手動ページビュー設定](https://developers.google.com/analytics/devguides/collection/ga4/views)
3. 測定ID（`G-...`）を`apphosting.yaml`の`NEXT_PUBLIC_GA_MEASUREMENT_ID`へ設定し、BUILD/RUNTIMEの両方へ渡します。これは公開用のIDです。値はビルドに埋め込まれるため、変更時は再ビルド・デプロイが必要です。空・形式不正の間はタグを読み込まず、GAへの通信もしません。
4. 本番のRealtimeレポートでページ閲覧を確認します。GA4側にイベント作成ルールや追加タグを設定して、自動計測を再開しないでください。

画面側は`src/lib/analytics.ts`と`src/components/analytics/`です。自動ページビューを無効にし、`/`・`/login`・`/home`へのページ遷移ごとに`page_view`を手動送信します。同じページでの再描画、クエリ・ハッシュだけの変更では追加しません。送信先のページURLは固定の公開ドメインとパスから作り、タイトルも固定値、参照元は空にします。新規登録はFirebaseの`getAdditionalUserInfo(result).isNewUser`を確認して`sign_up`を送り、認証方法名だけを追加します。再ログイン・認証方法の連携・ログイン状態の復元では送信しません。

ユーザーID・氏名・メール・店舗URL・メモ・評価・検索語・位置情報を計測イベントへ渡しません。Googleシグナルと広告のパーソナライズも無効です。GAはCookie等の識別子や端末情報を扱い、接続先にはIPアドレスも伝わるため、「個人を識別する情報が一切外部へ送られない」とは説明しません。[Googleのプライバシー設定](https://developers.google.com/tag-platform/security/guides/privacy)

ログイン前は「プライバシーについて」、ログイン後は「アカウント」→「利用状況の集計・アクセス解析」から、このブラウザーの計測を停止できます。設定は`localStorage`へ保存し、停止中はGoogleの無効化フラグとアプリ側の送信抑止を適用します。停止済みでページを開くとタグを読み込みません。設定を保存・参照できない環境も計測を止めます。タグのブロックや通信失敗はログイン・店舗保存を妨げません。BigQueryの件数集計はこのブラウザー設定とは別です。

### BigQueryの日次集計

Cloud Schedulerから認証付き内部API `/api/internal/metrics` を毎日0時台（日本時間）に呼び、前日の日付をキーに`analytics.daily_metrics`へ保存します。呼び出し元はOIDCトークンの宛先・メールアドレスを検証します。同じ日付の再実行はMERGEで置き換えます。

| 項目 | 集計の意味 |
| --- | --- |
| `total_users` / `new_users` | 現存する認証ユーザーのうち、対象日末までの登録数／対象日の登録数 |
| `active_users_7d` / `active_users_30d` | 認証情報の最終更新時刻（なければ最終ログイン時刻）を使った直近の利用者数 |
| `users_with_places` / `saved_places` | 集計時点でごみ箱以外の保存記録を持つ人数／保存件数 |
| `new_saved_places` | 対象日に作成された現存の保存記録数（ごみ箱に移したものも含む） |
| `visited_places` / `total_visits` | ごみ箱以外の訪問済み保存記録数／訪問回数の合計 |
| `date` / `generated_at` / `truncated` | 対象日／集計時刻／読み取り上限到達の有無 |

認証情報と保存記録をそれぞれ最大50,000件読み、上限に達した場合は`truncated`で示します。店舗URL、ユーザーID、メール、メモ、評価明細はBigQueryへ送りません。集計用にサーバー内で参照する情報と、BigQueryへ書く件数を区別します。

削除済みユーザーや消去済み記録を復元するイベントログは持たないため、これは厳密な過去日のスナップショットではありません。アクティブ数には日付境界から集計時点までの認証更新も入り、GA4のアクティブユーザー数とは定義が異なります。同日分を後で再実行すると、現存データの変化により結果が変わる場合があります。

`METRICS_ENABLED`、`METRICS_DATASET`、`METRICS_INVOKER`、`METRICS_URL`をサーバーへ設定します。BigQueryデータセット、呼び出し用サービスアカウント、権限、Schedulerの作成・有効化は別途必要です。日次走査のFirestore読み取りとBigQuery・Schedulerの費用を監視してください。

### 計測の検証

```sh
PATH="$(brew --prefix openjdk@21)/bin:$PATH" firebase emulators:exec --only auth,firestore --project demo-tsugikoko 'E2E_AUTH_EMULATOR=1 E2E_ANALYTICS=1 npx playwright test --workers=1'
```

測定IDはテスト専用値、Googleタグはネットワークを模擬します。スマホ・PCでページ遷移、新規登録と再ログイン・連携の区別、停止設定、タグ読み込み失敗を確認し、本番GA4へは送信しません。通常の認証E2Eでは測定IDを空にします。実際のタグによる送信とRealtimeへの反映は、プロパティ設定後に本番で別途確認します。
